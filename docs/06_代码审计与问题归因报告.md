## 二、重点 Bug 归因：扫描中目录树不能实时刷新

### 2.1 现象
扫描进行中，顶部进度条持续前进，但左侧目录树的可视节点数量与大小不随之刷新/增长，与「后端实际已扫描到的深度」不一致，需要手动展开或等扫描结束才对齐。

### 2.2 数据流（现状）
```
Rust run_background_scan
  ├─ 结构更新：仅 entry.depth()<=2 的目录进 pending_structures  → folder-structure-batch-updated
  ├─ 大小更新：所有遍历到的目录进 dir_stats → folder-size-batch-updated（200ms 节流）
  └─ 扫描结束才把 dir_stats 写入 size_cache
React scheduleUpdate(200ms 批处理) → setData → TreeView(data)
```

### 2.3 归因（按影响排序）

**C1（主因）结构更新深度封顶 + 延迟展开，导致深层节点扫描中不落地**
- 证据：[scanner.rs](file:///c:/Users/johnhelf/Pro/FolderExplorer/src-tauri/src/scanner.rs#L277) `if entry.depth() <= MAX_INITIAL_DEPTH`，`MAX_INITIAL_DEPTH=2`（[scanner.rs](file:///c:/Users/johnhelf/Pro/FolderExplorer/src-tauri/src/scanner.rs#L16)）。
- 影响：扫描中，第 3 层及以下目录**不会**以节点形式进入目录树；用户看到进度在走，但树的可视范围始终只有 0–2 层。深层结构需用户手动展开（[`expand_directory`](file:///c:/Users/johnhelf/Pro/FolderExplorer/src-tauri/src/commands.rs#L510)）才生成一次快照。这正是「实际扫描情况与目录树展示不一致」的直接来源。
- 定位：这是**有意的性能护栏**（避免前动向百万节点推送导致卡死/OOM），但牺牲了「实时一致性」。需要与产品体验做权衡，而非简单去掉。

**C2（次因）尺寸缓存仅在扫描结束时写入，扫描中途展开拿不到正确 size**
- 证据：[scanner.rs](file:///c:/Users/johnhelf/Pro/FolderExplorer/src-tauri/src/scanner.rs#L357-L360) `run_background_scan` 末尾才 `cache_lock.insert(...)`；而 `build_file_tree`（含 `expand_directory` 调用的 `build_file_tree(...,1)`）从 `state.size_cache` 读 size（[scanner.rs](file:///c:/Users/johnhelf/Pro/FolderExplorer/src-tauri/src/scanner.rs#L403-L474)）。
- 影响：扫描中途展开目录，子目录 size 命中部分扫描（`is_partial_scan=true`）→ 返回 `None` → 前端显示 "0 / Calculating…"；随后该节点在 size 更新事件里能否被覆盖，取决于其父路径是否命中 affected 集合，存在「展开后一直显示计算中」的观感。
- 结论：缓存**写入时机**与**读取时机**不一致，是实时性破坏的第二个明确根因。

**C3（代码隐患）`isRefreshing` 死守卫**
- 证据：[useAppLogic.ts](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/hooks/useAppLogic.ts#L59) 声明 `const isRefreshing = useRef(false);`；[L105-L107](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/hooks/useAppLogic.ts#L105-L107) `if (isRefreshing.current) return prev;`。但**全项目从未将 `isRefreshing.current` 置为 true**。
- 影响：该守卫是死代码，当前不阻断更新；但它是「用一处开关即可整体冻结目录树刷新」的后门，风险高，应清理或明确用途。

**C4（加重感知）多层节流叠加**
- Rust 200ms 发送 + 前端 200ms 批处理 + 图表 2s 节流；加上每次批处理触发 `sortChildren`，列表在大小变化中反复跳位，进一步放大了「刷新不及时/不一致」的感知。排序抖动问题已在旧 `analysis-plan.md` 中记录。

### 2.4 修复方向（仅建议，未实施）
> 下一阶段开发时优先验证：结构更新按「当前可视深度 + 1」增量推送、缓存边扫边写、展开时立即补拉该节点 size、去掉或正确使用 `isRefreshing`。

## 三、UI 代码规范性问题

（完整风格规范见 `07_UI设计风格规范.md`；此处仅列「代码层面违规/不一致」）

1. **`handleRefresh` 语义错乱 / 缺少「重新扫描当前文件夹」入口**
   - `useAppLogic.handleRefresh` 的真实行为是「重扫当前路径 `currentViewPath`」([useAppLogic.ts](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/hooks/useAppLogic.ts#L519-L523))，在 [App.tsx](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/App.tsx#L57) 传入 AppHeader；
   - 但 AppHeader 把该 `handleRefresh` 绑到「刷新磁盘列表」图标的 onClick 上（[AppHeader.tsx](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/components/AppHeader.tsx#L198-L205)），`title` 却是 `t('refreshDrives')`。
   - 结论：**UI 上点「刷新磁盘」实际会重扫当前文件夹**；真正刷新磁盘列表的 `refreshDrives`（[useAppLogic.ts](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/hooks/useAppLogic.ts#L251-L261)）**从未传给 AppHeader**，只在挂载时调一次。这是个明确的功能接线 bug，同时暴露出「缺少独立的、语义正确的『重新扫描当前文件夹』按钮」。

2. **i18n 违规**：`useAppLogic` 内手写英文错误串，绕过 t()：
   - [L329](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/hooks/useAppLogic.ts#L329) `"Please run this app inside Tauri..."`
   - [L438](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/hooks/useAppLogic.ts#L438)、[L480](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/hooks/useAppLogic.ts#L480) 等。

3. **垂直重复代码**：`analyzePath` / `analyzeFullDisk` / `toggleExpand` / `handleChartDrillDown` 四处各自复制了「读 pending → clear → applyBatchUpdates」约 12 行逻辑（[L355-L365](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/hooks/useAppLogic.ts#L355-L365) 等）。应抽出到 treeUtils 或成立独立工具函数。注意 `toggleExpand` 内注释也承认「由于清了队列，必须把更新应用到整棵树」——这是容易出错的高风险区（已留 note）。

4. **代码格式不统一**：`useAppLogic.ts` 多处缩进错乱（如 [L337-L343](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/hooks/useAppLogic.ts#L337-L343)、`finally` 块），建议统一 prettier。

5. **`categoryData` 统计口径 bug**：[L786](file:///c:/Users/johnhelf/Pro/FolderExplorer/src/hooks/useAppLogic.ts#L728-L786) 中 `categoryData` 依赖 `sizeMetric`，但求和用的是 `getNodeMetricSize(node)`（缺省参数 `'logical'`），即**切换「占用空间」口径对文件类型统计不生效**。

6. **`StatsGrid`/`TreeView` 的可用空间来自一次性 `availableDisks`**：仅在挂载时 `refreshDrives()` 获取，无定时刷新（见 §4 问题 Q3）。

7. **长/慢操作阻塞 async 运行时**：[commands.rs](file:///c:/Users/johnhelf/Pro/FolderExplorer/src-tauri/src/commands.rs#L905) `search_files`、[L536](file:///c:/Users/johnhelf/Pro/FolderExplorer/src-tauri/src/commands.rs#L536) `find_duplicates` 等 `async fn` 内做同步 `WalkDir` 全量遍历，无 `await`，会卡住 async executor 线程池；应改为阻塞式 `fn` 或 `tokio::task::spawn_blocking`。

## 四、登记：细节遗留问题清单

> 规划为后续功能开发的输入项，暂不实施。

### Q1 重新扫描当前文件夹
- Q1.1 缺少独立的「重新扫描当前文件夹」快捷按钮。逻辑 `handleRefresh` 已存在但被错误接为「刷新磁盘」（见 §3.1）。
- Q1.2 「刷新磁盘列表」（`refreshDrives`）无 UI 入口（建议在扫描下拉/标题栏补一个真正刷新磁盘的按钮）。

### Q2 系统可用空间
- Q2.1 `availableDisks`/`diskStats` 只在扫描时获取一次，**磁盘可用空间变化后不刷新**；重新扫描当前路径也不一定更新（`get_disk_stats` 仅随 `analyzePath` 调用一次）。
- Q2.2 StatsGrid/TreeView 头部展示的 used/total 均为旧快照。

### Q3 实时监控硬盘空间
- Q3.1 无定时器/轮询或后台事件来跟踪磁盘空间实时变化。
- 建议方案（待选型）：Tauri 前端 `setInterval` 调 `get_all_disk_stats`，或 Rust 端定时线程 + 事件推送；需评估轮询频率与耗电/IO 开销。

### Q4 扫描一致性（承接 §2）
- Q4.1 深层节点扫描中不落地，展开靠一次性快照。
- Q4.2 扫描中途展开目录 size 为 "计算中"，且可能不随之刷新。
- Q4.3 每次 `analyzePath` 会 `setExpandedPaths(new Set([root]))`，**重扫后所有已展开子目录全部收起**，破坏用户上下文与实时观测。

### Q5 视图切换 / 性能
- Q5.1 `categoryData` 在扫描期每次 200ms `data` 变化都全量递归累加当前子树，大目录下 O(N) 高频计算，有性能隐患。
- Q5.2 图表 2s 节流导致「扫描完成瞬间图表仍滞后」。
